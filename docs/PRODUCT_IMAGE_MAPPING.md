# 缺图示意与商品图片对应检查

## 图片显示顺序

分类卡片、查询结果及候选预览共用同一条显示路径：

1. 使用当前商品自己的真实正面包装图。
2. 大图加载失败时尝试同一商品的小图。
3. 两者均不可用时，根据商品名称或细分类选择对应的类别示意图，并标注“非实物包装，仅表示类别”。
4. 名称冲突、类型不明确时保留通用占位，不根据当前浏览的大分类强行配图，也不根据配料里的“牛奶”等词推断商品类型。

示意图由AI生成，已人工检查4×4图集的每一格及其映射。包含奶类饮品、酸奶、奶酪、蔬菜、水果、饮用水、果汁、茶饮、碳酸饮料、肉类、水产、蛋类、零食、调味品、餐食、粉状食品16类。它们不是具体SKU或品牌的包装照片，不表示真实配料、外观或销售规格。

“牛奶巧克力”和“牛奶饼干”归零食、“巧克力牛奶”归奶类、“奶茶”归茶饮、“奶粉”归粉状食品、“苹果汁”归果汁、“番茄酱”归调味品，避免简单关键词造成错配。分类是有限词表规则，无法理解所有商品名；不确定时采用通用占位，必要时完善词表与回归测试。

## 已修复的错配隐患

旧代码只验证图片来自 `images.openfoodfacts.org/images/products/`，没有核对它属于哪个条码。现在要求图片目录中的条码与当前商品一致；另一个商品的URL不会被请求，也不会因缓存或切换商品沿用。保留前导零规范化兼容，非法目录、外站URL和缺少条码的图片都被拒绝。

本地项目没有保存一份可逐张检查的真实商品图片库，本次可用运行缓存中也没有历史实物图片记录，因此没有把某张外部图片宣布为“已确认错图”。核对的是项目所有图片呈现路径和来源绑定，并修复可导致跨商品错配的逻辑。即使条码匹配，上游贡献者仍可能上传错误照片；本系统没有自动视觉识别整套公开图片数据库。使用时仍应通过原图与来源页核对实物。

## 资源与部署

`static/product-illustrations.png` 是经过检查的类别图集；固定坐标映射在 `services/product_illustration_service.py`。以静态资源复用，不为每个商品重复下载生成，也不需要额外的图片服务或API密钥。Streamlit配置启用 `server.enableStaticServing=true`；只有static目录中的公开图集由该服务提供，密钥和业务资料不放在static目录。

发布包已包含此图片资源，Docker的源码复制也会包含它。应用需要重启或完成自动部署后才会启用静态资源配置；单独刷新旧服务不能保证配置生效。

## 验证

- 全量154项测试通过，核心覆盖率93.20%；Mypy检查25个源文件通过，编译检查通过。
- 回归覆盖复合商品名、名称冲突、条码错配拒绝、同商品小图回退、真实图优先、牛奶与蔬菜连续切换、未知类型占位，以及发布包包含图集。
- 本机真实浏览器使用明确的界面测试样例验证桌面及390像素移动视口的静态图加载和“牛奶→蔬菜→牛奶”弹窗切换；截图保存在忽略目录 `runtime/illustration-validation/evidence/`，不等同于整个公网图片库审查。
